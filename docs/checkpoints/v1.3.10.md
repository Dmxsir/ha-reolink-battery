## 2. Product goal

Build a battery-safe Home Assistant integration for Reolink battery cameras, primarily validated against the **Argus 2E**.

The automatic recording path is:

```text
Reolink motion
  -> official Reolink Android notification
  -> Home Assistant Companion Last Notification sensor
  -> notification bridge
  -> persistent event queue
  -> closed-camera recording settle period
  -> short local Baichuan/P2P wake + login
  -> FileInfo recording lookup
  -> cmd13 prepare
  -> cmd8 full recording download
  -> exact MP4 validation + atomic save
  -> reolink_battery_recording_ready HA event
  -> optional Telegram automation
```

Battery safety is a primary design constraint. The automatic path must not maintain a permanent camera connection and must not poll the sleeping camera continuously.

Live View is separately available on demand through the integration/go2rtc, but Live View and recording must never open concurrent local Baichuan sessions to the same battery camera.

## 7. Notification bridge and automatic queue policy

The Android motion trigger path is considered operational.

Recent field diagnostics have repeatedly shown:

```text
configured: true
listener_active: true
last_event_matched: true
last_camera_mapped: true
last_event_queued: true
duplicate_rejected: false
```

The automatic queue/worker policy is battery-safe:

```text
RECORDING_SETTLE_SECONDS = 60.0
MAX_ATTEMPTS_PER_TRIGGER = 3
RETRY_DELAYS_SECONDS = (30.0, 60.0)
AUTOMATIC_EVENT_MAX_AGE = 600 seconds
```

Selection/recovery policy:

- newest explicitly activated fresh Android event wins;
- stale backlog must not wake the camera;
- failed events that exhaust retries are persistently deferred;
- deferred events are not automatically rearmed;
- startup recovery selects at most the newest fresh non-deferred event;
- a newer notification can preempt an older event during a retry wait;
- an active recording/download attempt is not cancelled merely because a newer motion arrives.

Expected policy strings:

```text
selection_policy = newest_activated_fresh_first
deferred_rearm_policy = explicit_only
startup_recovery_policy = newest_fresh_non_deferred_only
retry_preemption_policy = newer_notification_before_retry
```

## 8. Recording deduplication

Completed recordings use a persistent fingerprint so multiple Android notifications that map to the same physical SD recording do not cause repeated cmd13/cmd8 downloads or duplicate Telegram delivery.

Policy diagnostic:

```text
recording_dedupe_policy = persistent_candidate_fingerprint_before_cmd13
```

A duplicate recording can therefore complete the event without another media download.

## 11. Real field failure that led to v1.3.10

After installing v1.3.9, diagnostics exposed a different class of problem: **the recording attempt was not failing in UID/auth/FileInfo/download at all. It was stuck before UID discovery because Live View owned the shared camera-operation lock.**

### Field event timing

Latest event:

```text
notification time UTC: 2026-08-25T15:53:54.887000+00:00
notification local:    2026-08-25 18:53:54 Asia/Jerusalem
```

The worker correctly waited exactly 60 seconds:

```text
last_attempt_time UTC: 2026-08-25T15:54:54.887984+00:00
last_attempt local:    2026-08-25 18:54:54 Asia/Jerusalem
```

Diagnostics were exported around:

```text
2026-08-25T16:12:10Z
2026-08-25 19:12:10 Asia/Jerusalem
```

Therefore the attempt had been nominally running for about **17 minutes 15 seconds**.

### Worker signature

The worker still reported:

```text
running: true
attempts: 1
retries: 0
last_failure_stage: null
last_failure_type: null
last_file_saved: false
```

But UID telemetry was completely untouched:

```text
uid_resolve.timeout_seconds: 0.0
uid_resolve.send_rounds: 0
uid_resolve.datagrams_sent: 0
uid_resolve.elapsed_ms: null
uid_resolve.succeeded: false
```

The stream probe was also reset for the event but had never entered cmd13/cmd8:

```text
cmd13_frames: 0
cmd8_frames: 0
cmd8_attempted: false
file_write_attempted: false
file_bytes_written: 0
termination_reason: null
```

This is the key diagnostic distinction: **the attempt had started at the worker level, but camera transport had not started at all.**

### Live View signature at the same moment

Live View reported:

```text
active: true
video_consumers: 1
audio_consumers: 0
sessions_started: 1
sessions_completed: 0
```

The implementation showed why:

```text
Live View:
async with runtime.local_operation_lock:
    await async_stream_media(...)

Recording worker:
async with runtime.local_operation_lock:
    await async_prepare_download_for_event(...)
```

A Live View consumer can remain connected for many minutes. Because Live View held `local_operation_lock` for the entire session, the recording worker could wait indefinitely before UID discovery.

At the diagnostic snapshot the originally fresh event had become stale while the worker was still blocked:

```text
eligible_fresh_pending_count: 0
stale_pending_count: 18
```

This was a **local-operation lease starvation problem**, not a UDP media-transfer problem.

## 12. v1.3.10 design: recording priority over Live View

v1.3.10 keeps the important invariant:

```text
only one local Baichuan camera session at a time
```

It does **not** solve the starvation problem by opening recording and Live View concurrently.

Instead, the on-demand Live View hub now implements an explicit recording-priority gate.

### When a recording attempt starts

The worker calls:

```text
live_hub.async_pause_for_recording()
```

The hub:

1. increments a recording-priority depth;
2. prevents subscriptions/reconnects from starting a new Live View producer;
3. if a producer is active, sets its normal stop event;
4. waits for the Live View producer to finish and release `local_operation_lock`;
5. has a bounded 8-second cancellation fallback if a broken Live View source does not stop normally.

Only after the Live View producer has yielded does the existing base recording worker run normally and acquire the same `local_operation_lock` itself.

### While recording priority is active

New or reconnecting go2rtc/HTTP Live View consumers may register, but they are not allowed to start a camera producer.

This prevents the race:

```text
Live View stops
-> go2rtc immediately reconnects
-> Live View steals lock again
-> recording still starves
```

### After the recording attempt

The worker always calls:

```text
live_hub.async_resume_after_recording()
```

Queued Live View consumers may then start a fresh on-demand producer.

A failure to restart Live View is deliberately suppressed at this boundary so it cannot convert a successfully verified recording into a recording-worker failure.

### Expected user-visible behavior

If someone is actively watching Live View when a motion recording reaches its processing point:

- the Live View stream may briefly disconnect;
- the recording gets priority;
- after the attempt, go2rtc/consumer logic can reconnect Live View.

That interruption is intentional. Preserving a motion recording is higher priority than keeping an indefinitely open battery-camera preview session alive.

## 13. New v1.3.10 Live View diagnostics

The Live View session diagnostics now include:

```text

recording_priority_depth

```

Interpretation:

### `recording_priority_active`

`true` means a recording attempt currently owns the priority gate and new Live View camera producers must not start.

### `recording_priority_depth`

Internal bounded nesting count. Normal field behavior should generally be `0` when idle and `1` during one active recording attempt.

### `recording_preemptions`

Counts how many active Live View producers were explicitly asked to yield for recording attempts during the current integration runtime.

For the exact field scenario that motivated v1.3.10, the next test should produce:


if Live View is still active at the 60-second recording settle point.

## 18. Important interpretation rules

### A. Zeroed stream probe does not always mean recording logic failed

The worker resets stream telemetry at the beginning of a new attempt.

If the attempt is currently blocked before camera transport begins, the stream probe can legitimately show all zero values.

Always correlate with:

```text
recording_worker.running
recording_worker.last_attempt_time
recording_worker.uid_resolve.*
live_view.session.active
live_view.session.recording_priority_*
recording_worker.prior_attempt.*
```

### B. `running: true` does not prove network activity

The v1.3.9 field capture proved a worker could be `running: true` for more than 17 minutes while still waiting for `local_operation_lock` and before sending a single UID discovery datagram.

### C. Historical UDP missing count is not final active packet loss

Do not automatically interpret:

```text
udp_unresolved_missing_packet_count_at_disconnect
```

as the number of packets still missing from the final active receive window.

Prefer:

```text
udp_current_missing_packet_count_at_disconnect
udp_expected_next_seq_at_disconnect
udp_highest_network_seq_seen
udp_buffered_out_of_order_at_disconnect
```

### D. A newer notification can legitimately preempt a retry wait

If:

```text
retry_preemptions > 0
```

and the timestamps show a newer event, the old attempt not retrying after exactly 3/30 seconds may be correct policy rather than a failure.

### E. Partial files must remain rejected

Do not send or preserve an incomplete MP4 in production merely because it has a valid `ftyp` box.

The authoritative expected size and exact final size check remain the acceptance boundary.

## 19. Battery-safety invariants

Preserve these unless new real-hardware evidence requires a deliberate redesign:

1. No continuous polling of the sleeping camera for automatic motion detection.
2. Android push notification is the automatic motion trigger.
3. Keep the camera closed during the initial settle period.
4. No simultaneous recording and Live View local sessions.
5. Recording has priority when a fresh recording attempt is ready.
6. Automatic retries remain bounded.
7. Stale backlog does not repeatedly wake the camera.
8. Deferred events require explicit rearm policy.
9. Only exact verified MP4 files become final recordings.
10. Failed `.part` files are removed.

## 20. Current open technical question after v1.3.10

The immediate next question is no longer whether Live View can starve recording; v1.3.10 is specifically designed to prevent that.

The next physical test must determine what happens **after recording gets the lease**:

- Does UID resolution/auth/FileInfo succeed promptly while Live View was just stopped?
- Does the recording download now complete?
- If not, does it return to one of the already-known partial stream signatures?
- Does Live View reconnect correctly after the attempt?

Only after this arbitration behavior is physically validated should we decide whether another transport-level change is needed.
